# ADR-009 – System Bootstrap & Initialer Admin

Status: Accepted

---

## 1. Ziel

Definition eines sicheren, reproduzierbaren Mechanismus zur Ersteinrichtung
des Systems – insbesondere zur Anlage des initialen Admin-Benutzers.

Das System soll:

* Ohne manuelle Datenbankoperationen startbereit sein
* Für Self-Hosting-Nutzer einfach konfigurierbar sein
* Nach dem ersten Start keine offene Hintertür hinterlassen
* Open-Source-konform und dokumentierbar sein

---

## 2. Entscheidung: Konfigurationsbasiertes Bootstrap

Der initiale Admin-User wird beim ersten Start automatisch angelegt,
gesteuert durch Konfigurationswerte in `application.yml`.

---

## 3. Konfiguration

```yaml
app:
  bootstrap:
    enabled: true
    admin:
      username: admin
      email: admin@example.com
      password: changeme
```

---

## 4. Bootstrap-Logik

### Ablauf beim Start

```text
1. Anwendung startet
2. Flyway führt alle Migrationen aus
3. BootstrapService wird ausgeführt (ApplicationRunner)
4. Prüfung: Existiert bereits ein User mit Rolle ADMIN?
   - JA  → Bootstrap wird übersprungen, keine Aktion
   - NEIN → Admin-User wird anhand der Konfiguration angelegt
5. Anwendung ist betriebsbereit
```

### Idempotenz

Der Bootstrap läuft bei jedem Start – ist aber idempotent.
Existiert bereits ein Admin, passiert nichts.
Es wird kein zweiter Admin angelegt.

---

## 5. Implementierung

```java
@Component
@RequiredArgsConstructor
public class BootstrapRunner implements ApplicationRunner {

    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;
    private final BootstrapProperties properties;

    @Override
    public void run(ApplicationArguments args) {
        if (!properties.isEnabled()) return;

        boolean adminExists = userRepository.existsByRole(Role.ADMIN);
        if (adminExists) return;

        User admin = User.builder()
            .id(UUID.randomUUID())
            .username(properties.getAdmin().getUsername())
            .email(properties.getAdmin().getEmail())
            .password(passwordEncoder.encode(properties.getAdmin().getPassword()))
            .role(Role.ADMIN)
            .status(UserStatus.ACTIVE)
            .build();

        userRepository.save(admin);
        log.info("Bootstrap: Initial admin user created.");
    }
}
```

## 6. Sicherheitshinweise

### Standardpasswort

Das Standardpasswort `changeme` ist bewusst unsicher gewählt,
um Nutzer zur sofortigen Änderung zu motivieren.

Beim ersten Login wird eine Warnung angezeigt wenn das Passwort
noch dem konfigurierten Bootstrap-Wert entspricht.

### Empfehlung für Produktion

```yaml
app:
  bootstrap:
    enabled: true
    admin:
      password: ${ADMIN_BOOTSTRAP_PASSWORD}  # via Umgebungsvariable
```

### Bootstrap deaktivieren

Nach der Ersteinrichtung kann Bootstrap deaktiviert werden:

```yaml
app:
  bootstrap:
    enabled: false
```

Dies ist optional – durch die Idempotenz entsteht kein Sicherheitsrisiko
wenn Bootstrap aktiv bleibt.

---

## 7. Docker / Deployment

Für Docker-basierte Deployments werden die Werte über Umgebungsvariablen gesetzt:

```env
APP_BOOTSTRAP_ENABLED=true
APP_BOOTSTRAP_ADMIN_EMAIL=admin@meinblog.de
APP_BOOTSTRAP_ADMIN_PASSWORD=sicheresPasswort123
```

Dies entspricht dem Standard für Self-Hosted Open-Source-Anwendungen
(vergleichbar mit Ghost, Gitea, Nextcloud).

---

## 8. Flyway-Abgrenzung

Flyway verwaltet ausschließlich das **Schema** (DDL).
Bootstrap-Daten (initiale User) werden **nicht** per Flyway-Script eingefügt.

### Begründung

* Flyway-Scripts sind unveränderlich – ein Passwort im Script wäre ein Sicherheitsrisiko
* Konfigurationsbasierter Bootstrap ist flexibler und umgebungsabhängig
* Klare Trennung: Schema via Flyway, Initialdaten via Bootstrap

---

## 9. Nicht Bestandteil V1

* Setup-Wizard im Frontend
* E-Mail-Verifizierung bei Ersteinrichtung
* Automatische Bootstrap-Deaktivierung nach erstem Login
