# ADR-018 – Mehrsprachigkeit / i18n: Content, API & UI (V1)

Status: Accepted

---

## 1. Ziel & Kontext

Das Blog-CMS soll von Anfang an **mehrsprachig** sein. Start mit **Deutsch**
(Default) und **Englisch**, wobei das Hinzufügen weiterer Sprachen **ohne
Schema-Änderung** möglich sein muss.

Diese ADR legt das Gesamtkonzept fest über:

* die Trennung von **Oberflächensprache** und **Inhaltssprache**
* das **Content-Datenmodell** (Post, Category, Tag)
* die **Slug-/Eindeutigkeitsregeln** (ergänzt ADR-011)
* die **API-Locale-Negotiation** (ergänzt ADR-004)
* **lokalisierte Fehlermeldungen & UI-Strings** im Backend (ergänzt ADR-015)
* den **Frontend-i18n-Ansatz**
* die **Konfiguration** (ergänzt ADR-016)

---

## 2. Begriffe & Locale-Format

* **Locale**: Sprachkennzeichen nach **BCP 47** (`de`, `en`, später z. B.
  `fr`, `de-AT`). Speicherung als `VARCHAR(35)`.
* **Default-Locale**: `de`. Fallback-Sprache, wenn keine passendere ermittelbar ist.
* **Supported-Locales**: konfigurierte Allow-List (siehe Kapitel 13).
  Eine neue Sprache = Eintrag in der Konfiguration **+** Pflege von Inhalten.
  **Keine** Migration, kein Enum im Code.

> Bewusst **kein** Java-Enum für Sprachen: das widerspräche dem Ziel
> „Optionen freihalten". Sprachen sind Daten/Konfiguration, kein Code.

---

## 3. UI-Sprache vs. Inhaltssprache

Mehrsprachigkeit hat **zwei unabhängige Achsen**, die nie vermischt werden dürfen:

```text
Oberflächensprache (UI-Locale)   → Labels, Buttons, Menüs, Fehler-/Validierungs-
                                    meldungen – im Admin-Panel UND im öffentlichen
                                    Frontend. Reine Darstellung, kein Inhalt.
Inhaltssprache (Content-Locale)  → Sprache des Artikels / der Taxonomie (Kap. 5–7)
```

Beide sind **entkoppelt**: Ein Redakteur kann das Admin-Panel auf **Englisch**
stellen und dabei einen **deutschen** Beitrag schreiben.

### Entscheidung: UI-Sprache hängt am Benutzerkonto

| Variante                      | Verhalten                                             | Gewählt |
|-------------------------------|------------------------------------------------------|---------|
| Pro Benutzer                  | Persönliche Sprache, folgt dem Login gerätübergreifend | **Ja**  |
| Nur pro Browser               | Umschalter + `localStorage`, hängt am Gerät          | Ergänzung (s. u.) |
| Globale Systemsprache         | Eine Sprache für die ganze Installation              | Nein    |

* Neues Feld **`User.preferredLocale`** (`app_user.preferred_locale`, nullable).
* Nach dem Login initialisiert das Frontend seine UI-Sprache aus `preferredLocale`.
  Der Umschalter im Panel aktualisiert die gespeicherte Präferenz
  (sofort wirksam **und** persistiert am Konto).
* **Anonyme** Besucher des öffentlichen Frontends haben kein Konto → sie wählen
  die Sprache über einen **Umschalter im Header/Footer**. Die Wahl wird in
  `localStorage` persistiert und hat **Vorrang**. Auflösungsreihenfolge im
  Frontend:

  ```text
  1. explizite Wahl (localStorage)   ← Umschalter
  2. Accept-Language (Browser)       ← erster Besuch, noch keine Wahl
  3. default-locale                  ← letzter Fallback
  ```
* Bewusst **keine** globale, installationsweite „Systemsprache" – das widerspräche
  dem Mehrsprachigkeitsziel; jeder Nutzer wählt selbst.

Die **Inhaltssprache** bleibt davon unberührt: Sie wird pro Inhalt bzw. pro
Request (`?locale=`) gewählt (Kapitel 8), **nicht** aus `preferredLocale`
abgeleitet – `preferredLocale` dient dort höchstens als sinnvolle Vorbelegung.

## 4. Grundsatzentscheidung: zwei Übersetzungsmuster

Content zerfällt fachlich in zwei Klassen mit **unterschiedlichen** Anforderungen.
Deshalb werden bewusst **zwei** Muster verwendet:

```text
Post              → Translation-Group-Modell   (eigene Zeile je Sprache)
Category / Tag    → Translation-Table-Modell    (eine Identität, N Lokalisierungen)
```

| Aspekt                     | Post                              | Category / Tag                     |
|----------------------------|-----------------------------------|------------------------------------|
| Fachliche Natur            | Redaktioneller Artikel            | Taxonomie / geteiltes Konzept      |
| Lifecycle je Sprache       | **unabhängig** (Draft/Published)  | nicht vorhanden (nur Labels)       |
| Identität                  | Gruppe verbundener Zeilen         | **eine** Entität, gemeinsame ID    |
| Slug                       | je Sprache eigen                  | je Sprache eigen                   |
| Fehlt eine Übersetzung     | Inhalt in Sprache nicht sichtbar  | Fallback auf Default-Label         |

Begründung des Bruchs in der Konsistenz: Ein Post hat einen **eigenen
redaktionellen Lebenszyklus je Sprache** (DE veröffentlicht, EN noch Draft).
Eine Kategorie ist dagegen **ein Konzept** – ein Post darf seine Kategorie-
Zuordnung nicht sprachabhängig verlieren, sonst bricht das Filtern. Die
Anforderungen sind gegensätzlich, ein einheitliches Muster würde eine Seite
verschlechtern.

## 5. Datenmodell: Post (Translation-Group-Modell)

Jede Sprachversion ist eine **eigene** `posts`-Zeile mit eigener `id`, eigenem
`slug`, `status`, `published_at`, `title`, `excerpt`, `content`. Verbunden werden
Übersetzungen über eine gemeinsame `translation_group_id`.

### Neue Spalten

```sql id="post_i18n_columns"
ALTER TABLE posts ADD COLUMN locale               VARCHAR(35);
ALTER TABLE posts ADD COLUMN translation_group_id UUID;
```

### Constraints (ersetzt globalen Slug-Unique)

```sql id="post_i18n_constraints"
-- Slug ist pro Sprache eindeutig, nicht mehr global
ALTER TABLE posts DROP CONSTRAINT uq_posts_slug;
ALTER TABLE posts ADD  CONSTRAINT uq_posts_locale_slug   UNIQUE (locale, slug);

-- Höchstens eine Version je Sprache innerhalb einer Übersetzungsgruppe
ALTER TABLE posts ADD  CONSTRAINT uq_posts_group_locale  UNIQUE (translation_group_id, locale);
```

### Semantik

* **Neuer Post** → neue `translation_group_id`, gesetzte `locale`.
* **Übersetzung anlegen** → gleiche `translation_group_id`, andere `locale`.
* `category_id` und `post_tags` bleiben **je Zeile**: die DE- und die EN-Version
  referenzieren dieselbe Kategorie-/Tag-**ID** und rendern sie in ihrer Sprache.
* Der Status-Automat (ADR-013) bleibt **unverändert** – er operiert weiterhin
  auf einer einzelnen Post-Zeile.
* Eine Übersetzungsgruppe **muss nicht** mit der Default-Locale starten: Posts
  sind vollständig unabhängig, eine Gruppe darf z. B. nur eine `en`-Version
  enthalten. (Für Taxonomie gilt eine strengere Regel, siehe Kapitel 6.)

## 6. Datenmodell: Category & Tag (Translation-Table-Modell)

Basistabelle = **sprachneutrale Identität** (ID + Auditing). Übersetzbare Felder
(`name`, `slug`, `description`) wandern in eine Übersetzungstabelle.

```sql id="category_translation"
CREATE TABLE category_translation (
    id          UUID         NOT NULL,
    category_id UUID         NOT NULL,
    locale      VARCHAR(35)  NOT NULL,
    name        VARCHAR(100) NOT NULL,
    slug        VARCHAR(120) NOT NULL,
    description VARCHAR(500),
    created_at  TIMESTAMPTZ  NOT NULL,
    updated_at  TIMESTAMPTZ  NOT NULL,

    CONSTRAINT pk_category_translation      PRIMARY KEY (id),
    CONSTRAINT fk_cat_tr_category           FOREIGN KEY (category_id) REFERENCES categories (id) ON DELETE CASCADE,
    CONSTRAINT uq_cat_tr_category_locale    UNIQUE (category_id, locale),
    CONSTRAINT uq_cat_tr_locale_slug        UNIQUE (locale, slug)
);
```

```sql id="tag_translation"
CREATE TABLE tag_translation (
    id         UUID         NOT NULL,
    tag_id     UUID         NOT NULL,
    locale     VARCHAR(35)  NOT NULL,
    name       VARCHAR(80)  NOT NULL,
    slug       VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ  NOT NULL,
    updated_at TIMESTAMPTZ  NOT NULL,

    CONSTRAINT pk_tag_translation     PRIMARY KEY (id),
    CONSTRAINT fk_tag_tr_tag          FOREIGN KEY (tag_id) REFERENCES tags (id) ON DELETE CASCADE,
    CONSTRAINT uq_tag_tr_tag_locale   UNIQUE (tag_id, locale),
    CONSTRAINT uq_tag_tr_locale_slug  UNIQUE (locale, slug)
);
```

Die Basistabellen `categories` / `tags` behalten nur `id` + Auditing; die bisher
übersetzbaren Spalten werden nach der Datenmigration entfernt (Kapitel 14).
Es gibt damit **eine** Quelle der Wahrheit je Sprache.

### Pflicht-Invariante & Admin-Identität

* Jede Kategorie / jeder Tag **muss** mindestens eine Übersetzung in der
  **Default-Locale** besitzen. Diese Garantie trägt den Label-Fallback (Kapitel 9)
  und die Identifikation.
* In Admin-Listen wird eine Kategorie/ein Tag über ihre **Default-Locale-
  Übersetzung** angezeigt. Es gibt **keinen** separaten sprachneutralen `code` –
  die Default-Übersetzung ist die stabile Identität nach außen.
* Der Validator (Kapitel 13) verweigert das Löschen der Default-Locale-
  Übersetzung, solange die Kategorie/der Tag existiert.

## 7. Slug & Eindeutigkeit (Ergänzung ADR-011)

Diese ADR löst den in **ADR-011 §8** zurückgestellten Punkt „Mehrsprachige Slugs".

* Slugs sind ab jetzt **pro Locale eindeutig**, nicht global:
  * Post: `UNIQUE (locale, slug)`
  * Category/Tag: `UNIQUE (locale, slug)` in der jeweiligen Übersetzungstabelle
* Der Slug wird aus dem **lokalisierten** Titel/Namen der jeweiligen Sprache
  erzeugt; die Normalisierungsregeln aus ADR-011 §3 bleiben unverändert gültig.
* Kollisionsauflösung (Suffix `-2`, `-3`) läuft **innerhalb** einer Locale.
* Zwei Sprachversionen dürfen denselben Slug tragen
  (`.../de/mein-post` und `.../en/mein-post`), da `locale` Teil des Schlüssels ist.

## 8. API: Locale-Negotiation (Ergänzung ADR-004)

Auflösungskette (erster Treffer gewinnt):

```text
1. Query-Parameter   ?locale=de                 (explizit, primär, cache-key-freundlich)
2. Angemeldeter User → User.preferredLocale      (falls gesetzt; siehe Kapitel 3)
3. Header            Accept-Language             (Fallback)
4. Konfiguration     default-locale              (letzter Fallback)
```

Regeln:

* Schritt 2 betrifft primär **UI-/Fehlersprache**; die **Content-Auswahl** folgt
  weiterhin vorrangig dem expliziten `?locale` (Kapitel 3).
* Eine **nicht unterstützte** Locale wird nicht mit Fehler quittiert, sondern
  auf die Default-Locale zurückgeführt.
* Jede Response setzt **`Content-Language`** auf die tatsächlich aufgelöste Locale.
* Die aufgelöste Locale wird per `LocaleResolver`/Interceptor in den
  `LocaleContextHolder` gelegt und steht Services und `MessageSource` zur Verfügung.

## 9. Public API – Verhalten & Fallback

### Posts – strikt je Sprache, **kein** Body-Fallback

```http id="pub_posts_i18n"
GET /api/public/v1/posts?locale=de&category=backend&tag=spring
GET /api/public/v1/posts/{slug}?locale=de
```

* Die Liste liefert **nur** Posts der angeforderten Locale.
* Fehlt eine Übersetzung, erscheint der Post in dieser Sprache **nicht** und der
  sprachspezifische Detail-Slug liefert `404`.
  Begründung: Ein EN-Leser darf nicht stillschweigend deutschen Fließtext erhalten.
* Die Detail-Response enthält die verfügbaren Übersetzungen für den
  Sprachumschalter:

```json id="post_detail_translations"
{
  "id": "…",
  "locale": "de",
  "slug": "mein-post",
  "availableTranslations": [
    { "locale": "de", "slug": "mein-post" },
    { "locale": "en", "slug": "my-post" }
  ]
}
```

### Categories / Tags – Label-Fallback auf Default

* Rückgabe mit lokalisiertem `name`/`slug`.
* Fehlt die Übersetzung in der angeforderten Locale, wird das **Default-Locale-
  Label** geliefert (Taxonomie muss immer rendern). Ein `translated`-Flag kann
  dem Frontend die Ersatzsprache signalisieren.

## 10. Admin API – Verhalten

### Post-Übersetzung anlegen

```http id="admin_post_translation"
POST /api/admin/v1/posts
```

```json
{
  "locale": "en",
  "translationOf": "<translation_group_id | vorhandene post-id>",
  "title": "…", "excerpt": "…", "content": "…",
  "categoryId": "…", "tagIds": ["…"]
}
```

* Ohne `translationOf` → neue Übersetzungsgruppe.
* Mit `translationOf` → Anhängen an bestehende Gruppe (Constraint
  `uq_posts_group_locale` verhindert Doubletten je Sprache).
* Der Admin-Detail-View listet die Geschwister-Übersetzungen der Gruppe.

### Category-/Tag-Übersetzungen pflegen

Übersetzungen werden **pro Locale** über einen eigenen Sub-Pfad verwaltet
(gewählt gegenüber einer eingebetteten Map – klar, RESTful, einzeln pflegbar):

```http id="admin_category_translation"
GET    /api/admin/v1/categories/{id}/translations
PUT    /api/admin/v1/categories/{id}/translations/{locale}
DELETE /api/admin/v1/categories/{id}/translations/{locale}
```

(analog für `tags`).

Regeln:

* `PUT` legt eine Übersetzung an oder aktualisiert sie (Upsert je Locale).
* Nur **supported-locales** sind zulässig.
* Die **Default-Locale-Übersetzung** kann nicht gelöscht werden (Kapitel 6).

### Eigene UI-Sprache setzen

```http id="admin_user_locale"
PUT /api/admin/v1/users/me/preferred-locale
```

Setzt `User.preferredLocale` (Kapitel 3). Wirkt auf die Oberflächensprache des
angemeldeten Nutzers, nicht auf Inhalte.

## 11. Fehlermeldungen & UI-Strings im Backend (Ergänzung ADR-015)

* Spring **`MessageSource`** mit `messages.properties` (Default),
  `messages_de.properties`, `messages_en.properties`.
* Locale-Auflösung wie in Kapitel 8 (`LocaleContextHolder`).
* Das Fehlerformat aus ADR-015 bleibt strukturell gleich; ergänzt wird die
  Trennung zwischen **maschinenlesbar** und **menschenlesbar**:
  * `ErrorCode` (siehe `common/ErrorCode`) bleibt **sprachneutral & stabil** –
    Clients werten diesen aus.
  * `message` wird über den Message-Bundle-Schlüssel **lokalisiert**.
* Bean-Validation-Meldungen laufen ebenfalls über Bundle-Schlüssel.

```json id="error_i18n"
{
  "timestamp": "2026-08-16T12:00:00Z",
  "status": 404,
  "code": "POST_NOT_FOUND",
  "message": "Beitrag wurde nicht gefunden.",
  "path": "/api/public/v1/posts/mein-post"
}
```

## 12. Frontend-i18n

* Bibliothek: **react-i18next**.
* UI-Strings in `locales/de/*.json`, `locales/en/*.json` (getrennt von Content).
* **Sprachumschalter im Header/Footer** – für anonyme wie angemeldete Nutzer.
  * Anonym: Wahl wird in `localStorage` persistiert (Vorrang, siehe Kapitel 3).
  * Angemeldet: Wahl schreibt zusätzlich `preferredLocale` ans Konto (Kapitel 10);
    die UI-Sprache wird beim Login aus `preferredLocale` initialisiert.
* **Locale im URL-Pfad**: `/de/...`, `/en/...` – teilbar, SEO-freundlich,
  ermöglicht `hreflang`-Alternates. Beim Aufruf ohne Prefix (z. B. `/`) wird die
  Locale nach obiger Reihenfolge aufgelöst und auf die `/{locale}/`-URL umgeleitet.
* API-Aufrufe übergeben die aktive Content-Locale als `?locale=`.
* `<html lang="…">` sowie `hreflang`-Alternate-Links werden aus
  `availableTranslations` (Kapitel 9) erzeugt.

## 13. Konfiguration (Ergänzung ADR-016)

```yaml id="i18n_config"
app:
  i18n:
    default-locale: de
    supported-locales:
      - de
      - en
```

* **Neue Sprache hinzufügen** = Eintrag in `supported-locales` **+** Pflege der
  Inhalte/Bundles. **Keine** Schema-Änderung.
* Ein Validator lehnt Content/Übersetzungen in nicht unterstützten Locales ab.
* Default-Locale muss Teil der Supported-Locales sein (Startup-Check).

## 14. Migrationsplan (Flyway)

Fortführung der Konvention aus ADR-010 (nächste freie Nummern):

```text id="migration_plan"
V11__add_post_locale_and_translation_group.sql
  - Spalten locale, translation_group_id hinzufügen
  - Backfill: bestehende Posts → locale='de', je Zeile eigene translation_group_id
  - Spalten NOT NULL setzen
  - uq_posts_slug droppen; uq_posts_locale_slug + uq_posts_group_locale anlegen

V12__create_category_translation.sql
  - Tabelle category_translation anlegen
  - bestehende categories.name/slug/description → 'de'-Übersetzung migrieren
  - übersetzbare Spalten aus categories entfernen

V13__create_tag_translation.sql
  - Tabelle tag_translation anlegen
  - bestehende tags.name/slug → 'de'-Übersetzung migrieren
  - übersetzbare Spalten aus tags entfernen

V14__add_user_preferred_locale.sql
  - Spalte preferred_locale VARCHAR(35) NULL zu app_user hinzufügen
  - kein Backfill (NULL ⇒ Fallback über Accept-Language/Default, Kapitel 8)
```

Bestehende Daten bleiben vollständig erhalten und werden verlustfrei der
Default-Locale `de` zugeordnet.

## 15. Entscheidungsbegründung

### Warum Translation-Group für Posts

* Deckt den realen redaktionellen Bedarf: **unabhängige Veröffentlichung** je Sprache.
* Passt **fast 1:1** auf das bestehende `Post`-Entity und den Status-Automaten
  (ADR-013) – minimale Disruption.
* Eigene Slugs, Autoren und `published_at` je Sprache „gratis".
* Übersetzungen sind **inkrementell** – nicht jede Sprache muss existieren.

### Warum Translation-Table für Taxonomie

* Eine Kategorie/ein Tag ist **ein Konzept**; Post-Zuordnungen bleiben
  sprachübergreifend stabil, Filtern funktioniert über alle Sprachen.
* Lokalisierte Labels/Slugs ohne Fragmentierung der Identität.

### Warum UI-Sprache am Benutzerkonto (nicht global)

* Mehrere Redakteure teilen sich eine Installation – jeder arbeitet in seiner Sprache.
* Präferenz folgt dem Login gerätübergreifend, statt am Browser zu kleben.
* Eine globale Systemsprache widerspräche dem Mehrsprachigkeitsziel.

### Warum konfigurationsgetriebene Sprachen statt Enum/Spalten-pro-Sprache

* Ziel „weitere Sprachen freihalten" verlangt Erweiterung **ohne Schema-Änderung**.
* `title_de`, `title_en`-Spalten oder ein Sprach-Enum wären genau das Gegenteil.

---

## 16. Nicht Bestandteil V1

* Runtime-Sprachverwaltung über eine DB-Tabelle / Admin-UI
  (V1 ist konfigurationsgetrieben).
* Automatische maschinelle Übersetzung.
* Übersetzungs-Workflow-Status (z. B. „Übersetzung veraltet"-Flags) über den
  unabhängigen Lifecycle hinaus.
* Spezielle Behandlung regionaler Varianten (`de-AT`) über das BCP-47-Format hinaus.
* RTL-spezifisches Layout.
* Lokalisierte Media-Metadaten (Alt-Texte je Sprache) – spätere ADR.
