# ADR-012 – DTO- & Mapping-Strategie (V1)

Status: Accepted

---

## 1. Ziel

Festlegung, wie Domänenobjekte (JPA-Entitäten) von der über die API
ausgetauschten Repräsentation getrennt werden. Ziel ist ein stabiler
API-Contract (ADR-004), der von internen Modelländerungen entkoppelt ist.

---

## 2. Grundsatzentscheidung: Strikte Trennung Entity ↔ DTO

Entitäten werden **niemals** direkt über die API serialisiert oder
deserialisiert.

```text
Entity   →  internes Domänenmodell (JPA)
DTO      →  API-Contract (Request/Response)
```

### Begründung

* Verhindert versehentliche Preisgabe interner Felder (z. B. `password`)
* API-Contract bleibt stabil bei Entity-Refactorings
* Verhindert Lazy-Loading-Probleme bei der Serialisierung
* Ermöglicht gezielte Validierung pro Anwendungsfall

---

## 3. DTO-Typen pro Ressource

```text
{Resource}Request     – eingehende Daten (Create/Update), validiert
{Resource}Response    – ausgehende Daten
{Resource}Summary     – reduzierte Darstellung für Listen (optional)
```

### Beispiel Post

```text
PostRequest    – title, content, excerpt, categoryId, tagIds, status
PostResponse   – id, title, slug, excerpt, content, status,
                 author, category, tags, createdAt, updatedAt
PostSummary    – id, title, slug, excerpt, status, publishedAt
```

Getrennte Create-/Update-DTOs werden nur eingeführt, wenn sich die Felder
tatsächlich unterscheiden; sonst genügt ein `Request`.

---

## 4. Umsetzung als Java Records

DTOs werden als `record` implementiert:

```java
public record PostResponse(
    UUID id,
    String title,
    String slug,
    String excerpt,
    String content,
    PostStatus status,
    AuthorSummary author,
    CategorySummary category,
    List<TagSummary> tags,
    Instant createdAt,
    Instant updatedAt
) {}
```

### Begründung

* Unveränderlich, kein Boilerplate
* Klare Absicht: reine Datenträger
* Native Java-21-Sprachfeature, keine Zusatzabhängigkeit

---

## 5. Mapping-Verortung

* Mapping erfolgt in einer dedizierten `{Resource}Mapper`-Klasse pro Modul
* Manuelles Mapping (keine Mapping-Bibliothek in V1)
* Mapper sind zustandslose Spring-Beans (`@Component`)
* Controller rufen Service; Service arbeitet mit Entitäten und gibt DTOs zurück

### Schichtregel

```text
Controller  →  spricht ausschließlich DTOs
Service     →  nimmt Requests, gibt Responses, arbeitet intern mit Entities
Repository  →  ausschließlich Entities
```

Eine Entität verlässt niemals die Service-Schicht in Richtung Controller.

### Begründung „kein MapStruct/ModelMapper in V1"

* Wenige Entitäten, überschaubares Mapping
* Explizites Mapping ist lesbar und debugbar
* Vermeidet Annotation-Processor-Komplexität und Reflection
* Einführung einer Mapping-Bibliothek bleibt später möglich (isolierte Mapper)

---

## 6. Sensible Felder

* `password` erscheint in **keinem** Response-DTO (vgl. ADR-004 Sicherheitsregeln)
* Interne Audit-Felder (`createdBy`/`updatedBy`) werden nur bei Bedarf exponiert
* IDs von Beziehungen werden im Request als `categoryId`/`tagIds` (UUID)
  übergeben, nicht als verschachtelte Objekte

---

## 7. Validierung

* Bean Validation (`jakarta.validation`) auf `Request`-DTOs
* `@Valid` im Controller erzwingt Validierung vor Service-Aufruf
* Detaillierte Regeln pro Feld: siehe Fehler-/Validierungskatalog (ADR-015)

---

## 8. Nicht Bestandteil V1

* Automatisiertes Mapping (MapStruct/ModelMapper)
* HATEOAS / Hypermedia-Links
* Versionierte DTOs pro API-Version (erst bei `v2`)
* GraphQL-Typen
