# ADR-016 – Konfiguration & Spring Profiles (V1)

Status: Accepted

---

## 1. Ziel

Vereinheitlichung der Anwendungskonfiguration: Konfigurationsformat, Profil-Modell
und eine vollständige Referenz aller anwendungsspezifischen Properties. Behebt die
Inkonsistenz zwischen ADRs (`application.yml`) und dem initialen Projekt-Skeleton
(`application.properties`).

---

## 2. Grundsatzentscheidung: YAML

* Konfiguration erfolgt in **YAML** (`application.yml`)
* Die generierte `application.properties` wird durch `application.yml` ersetzt
* Begründung: verschachtelte `app.*`-Strukturen (Storage, Bootstrap, Security)
  sind in YAML deutlich lesbarer und konsistent mit ADR-008/009

---

## 3. Profil-Modell

```text
default   gemeinsame Basis (alle Umgebungen)
local     lokale Entwicklung (Secure-Cookie aus, Dev-DB)
prod      Produktion (Secrets via Env, Secure-Cookie an)
s3        aktiviert S3StorageService statt LocalStorageService (ADR-008, V2)
```

Aktivierung:

```yaml
spring:
  profiles:
    active: local
```

### Konfigurationsdateien

```text
application.yml           committet, keine Secrets
application-local.yml     lokal, gitignored (Beispiel: .example, ADR/README)
application-prod.yml      committet, Werte via ${ENV}
```

Secrets stehen **niemals** im Repository (vgl. ADR-014).

---

## 4. Vollständige `app.*`-Referenz

```yaml
app:
  # Media Storage (ADR-008)
  storage:
    backend: local              # local | s3
    location: /var/blogcms
    max-file-size: 10MB
    allowed-types:
      - image/jpeg
      - image/png
      - image/webp
      - image/gif
      - application/pdf

  # Bootstrap-Admin (ADR-009)
  bootstrap:
    enabled: true
    admin:
      username: admin
      email: admin@example.com
      password: ${ADMIN_BOOTSTRAP_PASSWORD}

  # Security / JWT (ADR-014)
  security:
    jwt:
      secret: ${JWT_SECRET}
      access-token-ttl: 15m
      refresh-token-ttl: 14d
    cookie:
      secure: true              # local: false
      same-site: Strict
```

Jeder `app.*`-Block wird auf eine typisierte `@ConfigurationProperties`-Klasse
gemappt (`StorageProperties`, `BootstrapProperties`, `SecurityProperties`).

---

## 5. Relevante `spring.*`-Properties

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/blogcms
    username: ${DB_USER}
    password: ${DB_PASSWORD}
  jpa:
    hibernate:
      ddl-auto: validate        # niemals update/create (ADR-010)
    open-in-view: false
  flyway:
    enabled: true
    locations: classpath:db/migration
  servlet:
    multipart:
      max-file-size: 10MB       # konsistent mit app.storage.max-file-size
      max-request-size: 12MB
```

### `open-in-view: false`

Erzwingt sauberes Laden in der Service-Schicht und verhindert Lazy-Loading
während der Serialisierung – konsistent mit der DTO-Strategie (ADR-012).

---

## 6. Env-Variablen (Deployment)

Konsistent mit ADR-009 (Docker) und ADR-014:

```env
DB_USER
DB_PASSWORD
JWT_SECRET
ADMIN_BOOTSTRAP_PASSWORD
SPRING_PROFILES_ACTIVE=prod
```

Spring Boot mappt `APP_STORAGE_LOCATION` etc. automatisch auf `app.storage.location`
(Relaxed Binding).

---

## 7. Validierung beim Start

* Fehlende Pflicht-Secrets (`JWT_SECRET`, DB-Zugang) → Startabbruch
* `@ConfigurationProperties`-Klassen nutzen `@Validated`
* Fail-fast statt Laufzeitfehler bei erster Nutzung

---

## 8. Nicht Bestandteil V1

* Externe Config-Server (Spring Cloud Config)
* Dynamisches Neuladen von Konfiguration zur Laufzeit
* Verschlüsselte Properties (Jasypt / Vault)
* Feature-Flags
