# ADR-004 – REST API Contract (V1)

Status: Accepted

---

## 1. Ziel

Definition eines konsistenten, erweiterbaren REST API Contracts für das Blog-CMS.

Der Fokus liegt auf:

* klarer Trennung von Public & Admin API
* stabiler URL-Struktur
* einfacher Erweiterbarkeit
* Open-Source-Freundlichkeit
* klaren Standards für Pagination, Filtering und Errors

---

## 2. API-Struktur

### Basis-Pfade

```text id="base_paths"
Public API:
  /api/public/v1/...

Admin API:
  /api/admin/v1/...
```

---

## 3. Designprinzipien

* REST-konform
* Ressourcenorientiert
* Keine Business-Logik in URLs
* Slugs für öffentliche Inhalte
* UUIDs intern
* Versionierung von Anfang an (`v1`)

---

## 4. Public API

### Posts

#### Liste Posts

```http id="pub_posts_list"
GET /api/public/v1/posts
```

Query Parameters:

```text
page        (default: 0)
size        (default: 10)
sort        (e.g. publishedAt,desc)
status      (default: PUBLISHED)
tag         optional
category    optional
```

---

#### Einzelner Post (Slug-basiert)

```http id="pub_post_slug"
GET /api/public/v1/posts/{slug}
```

---

### Kategorien

```http id="pub_categories"
GET /api/public/v1/categories
```

---

### Tags

```http id="pub_tags"
GET /api/public/v1/tags
```

---

## 5. Admin API

### Auth erforderlich (JWT)

---

### Posts

#### Alle Posts (inkl. Drafts)

```http id="admin_posts_list"
GET /api/admin/v1/posts
```

#### Post erstellen

```http id="admin_post_create"
POST /api/admin/v1/posts
```

#### Post aktualisieren

```http id="admin_post_update"
PUT /api/admin/v1/posts/{id}
```

#### Post löschen (soft delete empfohlen)

```http id="admin_post_delete"
DELETE /api/admin/v1/posts/{id}
```

---

### Kategorien

```http id="admin_categories"
POST /api/admin/v1/categories
PUT  /api/admin/v1/categories/{id}
DELETE /api/admin/v1/categories/{id}
```

---

### Tags

```http id="admin_tags"
POST /api/admin/v1/tags
PUT  /api/admin/v1/tags/{id}
DELETE /api/admin/v1/tags/{id}
```

---

### Media Upload

```http id="admin_media_upload"
POST /api/admin/v1/media
```

---

## 6. Pagination Standard

Alle List-Endpunkte verwenden Offset Pagination:

```json id="pagination_response"
{
  "content": [],
  "page": 0,
  "size": 10,
  "totalElements": 125,
  "totalPages": 13
}
```

---

## 7. Sorting & Filtering

### Sortierung

```text
sort=publishedAt,desc
```

---

### Filter

```text
status=PUBLISHED
tag=spring
category=backend
```

---

## 8. Error Handling Standard

Alle Fehler folgen einem einheitlichen Format:

```json id="error_format"
{
  "timestamp": "2026-06-09T12:00:00Z",
  "status": 404,
  "error": "Not Found",
  "message": "Post not found",
  "path": "/api/public/v1/posts/my-slug"
}
```

---

## 9. Slug-Regelung

* Slugs sind eindeutig
* Slugs sind öffentlich sichtbar
* Slugs werden nicht als interne IDs verwendet
* Änderungen am Titel verändern optional den Slug

---

## 10. Soft Delete

* Delete entfernt Inhalte nicht physisch
* Status wird auf `ARCHIVED` gesetzt
* Inhalte bleiben im System erhalten

---

## 11. Authentifizierung (Vorentscheidung)

* JWT basiert
* Access Token + Refresh Token (später ADR)
* Admin API vollständig geschützt

---

## 12. Nicht Bestandteil V1

* GraphQL
* Cursor Pagination
* Webhooks
* Public Write API
* API Keys für externe Systeme

# ADR-004 – Patch: User Management Endpoints

Status: Accepted (Ergänzung zu ADR-004)

---

## Änderung

Folgender Abschnitt wird in ADR-004, Kapitel 5 (Admin API) ergänzt.

---

## User Management

### Auth erforderlich: ADMIN

Alle User Management Endpoints sind ausschließlich für die Rolle `ADMIN` zugänglich.
EDITOR und AUTHOR haben keinen Zugriff.

---

### Endpoints

#### Alle Benutzer abrufen

```http
GET /api/admin/v1/users
```

Query Parameters:

```text
page    (default: 0)
size    (default: 10)
sort    (e.g. createdAt,desc)
role    optional – filtert nach Rolle (ADMIN | EDITOR | AUTHOR)
```

---

#### Einzelnen Benutzer abrufen

```http
GET /api/admin/v1/users/{id}
```

---

#### Benutzer anlegen

```http
POST /api/admin/v1/users
```

Request Body:

```json
{
  "username": "string",
  "email": "string",
  "password": "string",
  "role": "AUTHOR | EDITOR | ADMIN"
}
```

---

#### Benutzer aktualisieren

```http
PUT /api/admin/v1/users/{id}
```

Request Body:

```json
{
  "username": "string",
  "email": "string",
  "role": "AUTHOR | EDITOR | ADMIN"
}
```

> Passwortänderung erfolgt über separaten Endpoint (siehe unten).

---

#### Benutzer deaktivieren (Soft Delete)

```http
DELETE /api/admin/v1/users/{id}
```

* Setzt Status auf `INACTIVE`
* Kein physisches Löschen
* Bestehende Posts bleiben erhalten und dem User zugeordnet

---

#### Passwort zurücksetzen (Admin-seitig)

```http
POST /api/admin/v1/users/{id}/reset-password
```

Request Body:

```json
{
  "newPassword": "string"
}
```

---

### Response-Format (User)

```json
{
  "id": "uuid",
  "username": "string",
  "email": "string",
  "role": "AUTHOR | EDITOR | ADMIN",
  "status": "ACTIVE | INACTIVE",
  "createdAt": "ISO-8601",
  "updatedAt": "ISO-8601"
}
```

---

### Sicherheitsregeln

* Ein ADMIN kann sich nicht selbst deaktivieren
* Das Passwort wird niemals im Response zurückgegeben
* Rolle kann nicht auf eine höhere Stufe gesetzt werden als die eigene
  (verhindert Privilege Escalation)
