# ADR-010 – Datenbank-Schema & Flyway-Konventionen (V1)

Status: Accepted

---

## 1. Ziel

Festlegung verbindlicher Konventionen für das relationale Schema und dessen
Migration mit Flyway. Ziel ist ein reproduzierbares, konsistentes Schema, das
unabhängig von JPA-Auto-DDL entsteht.

Diese ADR konkretisiert ADR-002 (UUIDs, Auditing) und ADR-003 (Domänenmodell).

---

## 2. Grundsatzentscheidung: Schema-Hoheit bei Flyway

* `spring.jpa.hibernate.ddl-auto = validate` (niemals `update`/`create`)
* Das Schema wird **ausschließlich** über Flyway-Migrationen erzeugt
* Hibernate validiert nur, ob Entitäten zum Schema passen
* Kein Schema-Zustand entsteht implizit aus Entity-Annotationen

---

## 3. Namenskonventionen

```text
Tabellen        snake_case, Singular   → post, category, tag, app_user
Spalten         snake_case             → created_at, original_name
Primärschlüssel id (uuid)
Fremdschlüssel  {referenz}_id          → author_id, category_id
Join-Tabellen   {a}_{b}, alphabetisch  → post_tag
Indizes         ix_{tabelle}_{spalte}
Unique-Indizes  ux_{tabelle}_{spalte}
Fremdschlüssel  fk_{tabelle}_{referenz}
```

### `user` → `app_user`

`user` ist in PostgreSQL ein reserviertes Wort. Die User-Tabelle heißt daher
`app_user`. Die Entität heißt weiterhin `User`, gemappt via `@Table(name = "app_user")`.

---

## 4. Typ-Konventionen

```text
UUID        uuid            (nicht varchar)
Enum        varchar         via @Enumerated(EnumType.STRING) – niemals ORDINAL
Timestamp   timestamptz     (UTC, mit Zeitzone)
Text/Markdown text
Kurztext    varchar(n)      mit expliziter Länge
```

### Begründung Enum als String

* Ordinal bricht bei jeder Umsortierung des Enums
* Datenbank bleibt menschenlesbar und stabil gegenüber Code-Änderungen

### Begründung `timestamptz`

* Speicherung in UTC, Zeitzonen-Konvertierung im Frontend
* Konsistent mit ISO-8601-Ausgabe der API (ADR-004)

## 5. Migrations-Konventionen

### Dateinamen

```text
V{version}__{beschreibung}.sql

V1__create_app_user.sql
V2__create_category.sql
V3__create_tag.sql
V4__create_post.sql
V5__create_post_tag.sql
V6__create_media.sql
```

### Regeln

* Versionierte Migrationen (`V`) sind **unveränderlich** nach dem Merge
* Ein Fehler in einer gemergten Migration wird per **neuer** Migration korrigiert
* Kein `R__` (Repeatable) für Schema in V1
* Keine Initialdaten in Migrationen (User-Bootstrap via ADR-009)
* Ein logischer Schritt pro Migration

### Speicherort

```text
src/main/resources/db/migration/
```

## 6. Constraints & Indizes (V1)

```text
app_user
- ux_app_user_username   (unique)
- ux_app_user_email      (unique)

post
- ux_post_slug           (unique)
- ix_post_status
- ix_post_author_id
- ix_post_category_id
- fk_post_author  → app_user(id)
- fk_post_category → category(id)  (nullable)

category
- ux_category_slug       (unique)

tag
- ux_tag_slug            (unique)

post_tag
- PK (post_id, tag_id)
- fk_post_tag_post → post(id)
- fk_post_tag_tag  → tag(id)
```

---

## 7. Referentielle Integrität & Soft Delete

Konsistent mit ADR-002 (kein Hard Delete):

* Fremdschlüssel verwenden **kein** `ON DELETE CASCADE`
* Löschen erfolgt über Statusübergänge, nicht über `DELETE`-Statements
* Referenzen bleiben dauerhaft gültig

---

## 8. Nicht Bestandteil V1

* Partitionierung
* Materialized Views
* Datenbank-seitige Trigger
* Repeatable Migrations
* Mehrere Schemata / Multi-Tenancy
